Step 1 — Embedding Model: BAAI/bge-m3

Model: BAAI/bge-m3 via SentenceTransformers · Singleton loaded once at startup (rag_engine.py:90) — shared across all 5 import sites
Instruction prefix: "Represent this EPUB issue for retrieval: {text}" prepended to every chunk at index time
Normalization: normalize_embeddings=True — cosine similarity = dot product (faster in ChromaDB HNSW)
Thread-safe: Double-checked lock prevents concurrent double-loads

Why BGE-M3?

State-of-the-art multilingual model. Handles EPUB-specific vocabulary (CSS selectors, XHTML tags, BCP-47 language codes) better than general models. Supports up to 8192 tokens — important for long CSS files.

Two uses in the pipeline

1. Index time: embed chunks before writing to ChromaDB
2. Query time: embed the EPUB issue description before searching
Same model, same instruction prefix — ensures query/document vector space alignment

Also used for text diffing

compute_similarity(text1, text2) computes cosine similarity between two text passages. Thresholds: >0.98 = identical, >0.95 + low fuzzy = formatting mismatch, <0.85 = high-risk divergence

Step 2 — SmartChunker: 4 Strategies

File type drives strategy selection automatically via auto_chunk(content, content_type)

CSS → css_rule

Rule-block chunking

Parses CSS by brace depth. Each chunk = one complete selector { declarations } block. Stores selector, line_start, line_end in metadata.

Cap: 800 chars per chunk. Falls back to sliding_window if no blocks found.
Used by: EPUBContentIndexer + KB CSS indexing

HTML/XHTML → hierarchical

Heading-anchored chunking

Parses HTML with BeautifulSoup. Splits at h1 / h2 boundaries. Each chunk stores its parent h1 and h2 in metadata — preserves document structure.

Max 512 tokens per chunk. Tags: h1 h2 h3 p li td th
Cap: 20 HTML files, 60 KB per file
Used by: EPUBContentIndexer HTML indexing

JS → sliding_window

Sliding window

512-token window, 128-token overlap. Each chunk includes the end of the previous chunk so no context is lost at boundaries.

Also fallback for any content that doesn't match other strategies.
Used by: KB JS indexing, any unknown file type

Prose / KB rules → semantic

Sentence-boundary chunking

Splits on [.!?]\s+. Accumulates sentences until ~300 tokens, then flushes.

Best for KB rule descriptions, OPF metadata summaries, accessibility guidance — natural language that benefits from sentence integrity.
Used by: KB entry indexing, OPF metadata

Step 4 — Hybrid Search: Dense + BM25 Fusion

Formula: score = 0.65 × dense_cosine + 0.35 × BM25_normalized
Dense candidates: limit × 2 fetched from ChromaDB HNSW for re-ranking headroom
BM25 tokenizer: lowercases, splits on non-alphanumeric, preserves hyphens (critical for CSS property names like font-weight)
BM25 scope: only static collections (kb_css, kb_js, epub_rules, issue_patterns) — per-run epub_* collections use dense-only (small + ephemeral)

Why 65/35 split?

Dense search (BGE-M3) captures semantic meaning — good for "CSS property invalid" matching "unsupported CSS declaration". BM25 adds exact-keyword recall — good for matching specific property names like font-weight or extrabold. 65/35 favours semantics while ensuring keyword-heavy EPUB rules still score well.

BM25 index lifecycle

Built lazily on first query per collection. Cached in module-level _bm25_cache dict for 30 min (BM25_TTL). Rebuilds automatically on next query after TTL expires. Per-run epub_* collections are skipped — not worth BM25 indexing since they're small and short-lived.

Step 5 — CAG Cache: Cache-Augmented Generation

What it does: Pre-loads top-100 KB chunks from Redis into Python process memory (dict). Reduces retrieval latency for the most-used KB entries to zero (no ChromaDB round-trip).
Query cache: cag_query:{hash(query)} stored in Redis with 30-min TTL — repeated queries for the same issue type skip all embedding + search
Refresh: Background asyncio task refreshes every 30 min

Step 6 — Per-EPUB Content Indexing at Autofix Start

When: Fired as a non-blocking background task the moment autofix begins (does not delay the fix pipeline)
What gets indexed: Up to 10 CSS files (css_rule strategy) + 20 HTML files (hierarchical, capped at 60 KB each) + OPF metadata (semantic, first 2000 chars of OPF + extracted key fields)
Why: Gives KBAgent grounding in this specific EPUB's CSS patterns and HTML structure, not just generic EPUB rules

Known Gaps & Improvement Opportunities

#GapImpactSuggested Fix
1 KB context not stored in fix_trace RAGAS Context Precision = N/A; LLM judge can't measure faithfulness meaningfully Add kb_context field to each fix_trace entry in _run_autofix_job
2 epub_{run_id} collections never cleaned up ChromaDB grows unboundedly with one collection per autofix run Delete collection in finally block of _run_autofix_job, or run a TTL cleanup job
3 Token count uses word count (len(text.split())), not real tokens Chunks may exceed model context window on dense text (e.g. minified CSS) Use a real tokenizer (tiktoken or SentenceTransformer's tokenizer) for accurate chunk sizing
4 BM25 skips per-run epub_* collections Keyword recall is lower when searching the per-EPUB context (CSS selector names, class names) Build a lightweight in-memory BM25 index for the epub_{run_id} collection at index time (it's small — typically <200 chunks)
5 Instruction prefix used at index time but not explicitly at query time Minor vector space misalignment; BGE-M3 is robust enough to compensate but not optimal Also prepend the same instruction prefix to the query embedding in hybrid_search and cag.py
